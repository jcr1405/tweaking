Your job is to connect these existing components correctly and make Presence's actual capabilities match its architectural design.

## PHASE 1 — FIX CONVERSATIONAL ROUTING (HIGHEST PRIORITY)
### Current problem
`ComplexityClassifier` relies heavily on keyword matching and starting-prefix checks.
The current routing path in `AgentSession.execute_turn()` can classify conversational questions as LONG_RUNNING or COMPLEX and preempt the normal conversational model before it sees the user's message.
For example, asking:
"What are your capabilities? Explain whether you can inspect projects, run tests and operate Windows."
can trigger TDEL because it contains words such as `inspect`, `run tests` and `desktop`.
Even worse, the classifier does not understand explicit negative instructions such as:
"This is a question, NOT a task. Do not invoke TDEL."
### Required behaviour
Separate conversational intent from operational intent.
Implement a deterministic conversation-first routing policy that considers the complete user request rather than blindly scanning keywords.
Recognize these as conversational:
- Questions about Presence's capabilities.
- Explanations of how Presence works.
- Architectural discussions.
- Requests for advice or recommendations.
- Hypothetical scenarios.
- Questions mentioning tools, shell commands, file edits or desktop operations without requesting their execution.
- Questions containing operational keywords inside quotations, examples, code blocks or negative instructions.
Recognize these as operational only when the user actually requests an action.
Examples:
- "What can you do with my files?" → CONVERSATION.
- "Explain how you would debug this project." → CONVERSATION.
- "Could you inspect my project and identify the failing tests?" → OPERATIONAL.
- "Run the tests in this project and report failures." → OPERATIONAL.
- "Create a plan for updating the project, but do not execute it." → PLAN_ONLY.
- "Execute this approved plan." → OPERATIONAL.
### Architecture requirements
1. Conversational questions must reach the normal conversational provider path without initializing TDEL.
2. Operational requests may enter the existing planning and execution path.
3. Explicitly requested plan-only operations must not execute automatically.
4. Ambiguous requests should default to conversation or ask for clarification rather than silently executing.
5. Negation, hypothetical language, quoted instructions and examples must not be treated as execution authorization.
6. Preserve explicit tool invocation and existing operational workflows.
7. Do not add another LLM-based intent classifier that introduces unnecessary latency or an additional provider dependency.
8. Use the existing classifier and routing boundary, improving them with a clear intent decision.
9. Avoid breaking normal short commands such as "search the web for..." or "open this file..." when their intent is genuinely operational.
10. Make the intent classification observable through structured logs, without logging sensitive prompt contents.
### Required regression tests
Test at least 25 representative prompts covering:
- Capability questions.
- Architecture explanations.
- System design discussions.
- Operational requests.
- Plan-only requests.
- Explicit execution requests.
- Negative instructions.
- Hypothetical examples.
- Quoted commands.
- Long prompts containing words such as `run tests`, `inspect`, `shell`, `desktop` and `delete` without requesting execution.
The original failed capability-audit prompt must be a regression test.
Assert that conversational prompts do not emit `PLAN_CREATED`, do not invoke TaskPlanningService and do not create DAGs.

## PHASE 4 — IMPLEMENT A REAL USER-FACING APPROVAL FLOW
### Current problem
The backend has consent-token issuance and verification infrastructure, but the TUI has no actual approval component.
Consequently, protected operations can reach NEEDS_CONSENT or PERMISSION_DENIED without a proper way for the user to authorize them.
### Required integration
Connect the existing consent infrastructure to actual TUI interactions.
Do not create a second authorization system.
When an operation requires approval:
1. The operation must pause before the protected side effect.
2. The workflow must enter the existing WAITING_FOR_APPROVAL or AWAITING_APPROVAL state.
3. The TUI must display a clear approval request.
4. The user must be able to approve or reject through actual TUI keyboard/input interaction.
5. Approval must resume only the specifically authorized operation.
6. Rejection must cancel that operation safely.
### Approval display
Show:
- Requested operation.
- Target application, file, process or resource.
- Relevant parameters.
- Why approval is needed.
- Expected side effects.
- Whether the operation is reversible.
- Expiry time.
- Exact operation scope.
Provide clear Approve and Reject controls compatible with the current TUI rendering architecture.
### Cryptographic consent requirements
Reuse existing `issue_consent_token()` and `verify_consent_token()` implementations.
Tokens must be bound to:
- Exact user identity.
- Conversation identity.
- Task/workflow identity.
- Exact action and arguments.
- Expiry.
- Single-use nonce or equivalent anti-replay mechanism.
A token for one operation must never authorize another operation.
The model must never issue its own approval token.
Timeout, rejection, invalid signatures, replay and cross-conversation attempts must fail closed.
Never treat an LLM-generated message such as "the user approves" as authorization.
The approval must originate from the real user interaction path.
### Required tests
- TUI renders an actual approval request.
- Workflow pauses before the side effect.
- Explicit user approval resumes the correct operation.
- Rejection prevents the side effect.
- Expired consent is rejected.
- Replayed consent is rejected.
- Tampered parameters invalidate consent.
- Cross-conversation consent is rejected.
- Model-generated approval statements have no effect.
- Application restart does not turn a pending approval into automatic approval.
